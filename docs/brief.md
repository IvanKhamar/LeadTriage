## 2. What the system does (the story for the README)

Verde Kitchen is an invented healthy food and drinks brand (see its README). Its website gets messages from a
contact form: product questions, "where can I buy it", wholesale and stockist requests, partnership offers,
complaints, spam. Today a manager would read and sort them by hand. LeadTriage does it automatically:

1. A visitor fills in the contact form on the Verde Kitchen site (Drupal).
2. Drupal saves the message and sends it, server to server, to the LeadTriage API.
3. The FastAPI service validates it and forwards it to an n8n webhook.
4. n8n normalises the data, asks the Python service for deterministic enrichment,
   asks Claude to classify the lead, checks for duplicates and writes the result to Airtable.
5. High-priority leads trigger a notification. Failures are retried, then logged for a human.

Result for the manager: an Airtable table with every lead already sorted, prioritised,
summarised, with a draft reply ready to review.

LeadTriage must also work **without Drupal**: it has its own small demo form and a mock LLM mode,
so anyone who clones the repo can run it with Docker only.

## 3. Lead intake contract v1 (shared with the Drupal brief — keep both copies identical)

Two entry points, one payload:

| Endpoint | Caller | Auth |
|---|---|---|
| `POST /api/leads` | LeadTriage's own demo form (browser, same origin) | none; rate limit + honeypot |
| `POST /api/sources/{source}/leads` | server-to-server sources, first one `verde-kitchen` | header `X-Source-Token`, one token per source, compared with `hmac.compare_digest` |

Request body (JSON):

```json
{
  "externalId": "verde-kitchen:contact:123",
  "name": "Olena Test",
  "email": "olena@example.com",
  "phone": "+380501234567",
  "message": "Do you deliver to Lviv? We run a small cafe and want to order wholesale.",
  "consent": true,
  "locale": "uk",
  "pageUrl": "https://verde.ddev.site/uk/contact",
  "submittedAt": "2026-11-21T10:15:00+02:00"
}
```

- `externalId` (required for sources, ≤ 100 chars): the source's own id. Sending the same id again is **idempotent**:
  answer `200 {"status":"duplicate","leadId":...}` and do not process it twice. This makes source retries safe.
- `name` 2–100, `email` valid, `phone` optional, `message` 10–2000, `consent` must be `true`,
  `locale` `uk`/`en`, `pageUrl` optional, `submittedAt` ISO 8601 with zone.
- Answers: `202 {"status":"received","leadId":"..."}`; `400` validation (ProblemDetails, field names only, no
  internals); `401` wrong or missing token; `413` body too large; `429` rate limit; `503` when n8n cannot be reached
  (the source must retry later).
- `docs/lead-intake-contract.md` holds this section; an OpenAPI file is generated by FastAPI.

## 4. Architecture

```
Verde Kitchen (Drupal) ─┐
                        ├─► FastAPI ──► n8n Webhook (header auth)
Demo form (browser) ────┘                 │
                                          ├─► Normalise (Code / Set nodes)
                                          ├─► HTTP Request ► FastAPI /api/enrich
                                          ├─► Claude API (or mock) ► validate JSON
                                          ├─► Airtable: search by email ► create or update
                                          ├─► IF priority = high ► notify
                                          └─► Respond to Webhook (lead id, status)
Error Trigger workflow ──► Airtable "Errors" table
```

Draw it as a Mermaid diagram in the README.

| Part | Tech | Job |
|---|---|---|
| `app/` | Python 3.13, uv, FastAPI, Pydantic v2, pydantic-settings, httpx | Intake API (contract above), demo form page, `/api/enrich`, forwarding to n8n |
| `web/` | Plain HTML, CSS, JavaScript (no framework) | Demo form, client-side validation, success and error states |
| `n8n/workflows/` | n8n (self-hosted in Docker) | Exported workflow JSON: main flow + error flow |
| Airtable base | Airtable free plan | Tables `Leads` and `Errors` (schema in `docs/airtable-schema.md`) |
| `docker-compose.yml` | Docker | n8n + the FastAPI app, ports bound to `127.0.0.1` only |

Secrets never reach a browser: the demo form talks only to FastAPI, and FastAPI adds the n8n webhook token on the
server side. Drupal calls FastAPI from its server, never from the visitor's browser.

## 5. Functional requirements

### 5.1 Intake (`app/`)
- Pydantic models for the contract; body size limit; per-IP rate limit on `/api/leads` (e.g. 5 per minute).
- Honeypot filled → answer 202 as usual but do not forward (silent drop, logged without personal data).
- Idempotency store for `externalId` (SQLite file in a git-ignored volume is enough; explain the choice).
- Forward to n8n with header `X-Webhook-Token` (from `.env`), timeout, one retry on network error; n8n down → 503.
- `source` is recorded on every lead (`verde-kitchen`, `demo-form`).

### 5.2 `POST /api/enrich` (called by n8n)
Deterministic, no AI: email domain, free-mail flag (gmail, ukr.net, …), disposable-email flag (small static list),
phone country, message length, language guess (simple heuristic). Protected by its own token.

### 5.3 n8n main workflow
- **Webhook** node with Header Auth credential.
- **Normalise**: trim, lower-case email, collapse whitespace, keep `source`, `externalId`, `receivedAt`
  (ISO 8601 with zone; display Kyiv time).
- **Enrich**: HTTP Request to `/api/enrich`.
- **Classify** with Claude (HTTP Request to the Anthropic Messages API or the n8n Anthropic node — choose one and
  explain why in the README). Output JSON:
  `category` (enum: `product_question`, `where_to_buy`, `wholesale`, `order_issue`, `complaint`, `partnership`,
  `spam`, `other`), `priority` (`high` / `medium` / `low`), `language` (`uk` / `en` / `other`),
  `summary` (≤ 200 chars), `replyDraft` (≤ 600 chars, in the lead's language), `confidence` (0–1).
- **Validate** the LLM output: parse, check enums and lengths. Invalid → `category = other`, `needsReview = true`,
  keep the raw text for debugging.
- **Mock mode**: `LLM_MODE=mock` returns a fixed, valid classification without calling the API (tests, demos,
  people who clone the repo).
- **Deduplicate**: search Airtable `Leads` by email in the last 30 days; existing → update and append the new message
  to history; new → create.
- **Notify** when `priority = high`: Airtable view "Urgent" first; Telegram bot optional behind `NOTIFY_TELEGRAM=true`.
- **Respond to Webhook** with the lead id and status.
- Model name, max tokens and price per million tokens come from env/config, never hard-coded
  (example model: `claude-haiku-5-5`). Log `inputTokens`, `outputTokens`, `costUsd`, `latencyMs` per lead.

### 5.4 Error handling (a key point for the interview)
- Retry On Fail with wait on HTTP, Claude and Airtable nodes (e.g. 3 tries, growing wait).
- Separate **Error Trigger** workflow: workflow name, node, message (no secrets, no full payloads), execution id and
  time → Airtable `Errors`.
- Claude unavailable after retries → save the lead anyway with `needsReview = true`. No lead is ever lost:
  FastAPI answers 503 when it cannot hand a lead to n8n, and the source retries (Drupal keeps it in its queue).
- Document each failure path in `docs/error-handling.md` and test it (wrong key, mock failure mode, Airtable down,
  n8n down).

### 5.5 Prompt-injection safety
The lead message is untrusted input. The prompt puts it inside clear delimiters and tells the model to treat it as
data. Model output is only used as data: enums are validated, nothing is executed or sent automatically because of
model text, `replyDraft` is only a draft for a human. Mention this in the README.

## 6. Airtable

`docs/airtable-schema.md` describes the base so the user can create it by hand in a few minutes:

- `Leads`: Source, ExternalId, Name, Email, Phone, Message, History, Category (single select), Priority
  (single select), Language, Summary, ReplyDraft, Confidence, NeedsReview (checkbox), EmailDomain, FreeMail,
  Disposable, InputTokens, OutputTokens, CostUsd, LatencyMs, ReceivedAt, Status (single select: new / in progress /
  done).
- `Errors`: Workflow, Node, Message, ExecutionId, OccurredAt.
- Views: "Urgent" (priority high, status new), "Needs review", "Wholesale".

Access: a personal access token with only `data.records:read`, `data.records:write`, `schema.bases:read`,
limited to this one base. It lives only in n8n's credential store.

- Secrets (`ANTHROPIC_API_KEY`, Airtable token, `WEBHOOK_TOKEN`, `ENRICH_TOKEN`, `SOURCE_TOKEN_VERDE_KITCHEN`,
  `N8N_ENCRYPTION_KEY`, Telegram token) only in the git-ignored `.env` or n8n's encrypted credential store.

- `.gitignore` from the start: `.env`, `.venv/`, caches, the n8n data volume / `.n8n/`, `*.sqlite`, data exports.
- **Workflow export**: no credential values, no `pinData` (pinned test data), no real e-mails. `tools/export_workflows`
  exports via the n8n CLI and strips `pinData`; a pytest test checks every file in `n8n/workflows/` for these rules
  and that the webhook uses header auth.
- gitleaks in CI on every push and PR. Check the diff before each commit.
- Only invented leads (Faker or hand-written, `example.com` addresses) in tests, seeds, screenshots and the demo.
- Containers listen on `127.0.0.1` only; how the Drupal container reaches the API is in section 9.
- FastAPI: no exception details in 500 errors, CORS only for its own origin, security headers on the form page.
